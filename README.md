# Marketplace API

## 1. Що це за сервіс

Marketplace API - це backend для онлайн-маркетплейсу, де продавці публікують товари, покупці оформлюють замовлення, а система контролює залишки, платежі та сповіщення. Сервіс вирішує проблему узгодженого оформлення замовлення: товар не має бути проданий більше разів, ніж є на складі, а повторний запит клієнта не повинен створювати дубль замовлення.

Основні ролі:

- Покупець переглядає каталог, створює замовлення та бачить статус оплати.
- Продавець керує товарами, цінами та залишками.
- Адміністратор модерує товари та розбирає спірні замовлення.

User stories:

- Як покупець, я хочу переглядати товари з пагінацією, щоб швидко знаходити доступні позиції.
- Як покупець, я хочу створити замовлення з кількома товарами, щоб купити все одним checkout.
- Як продавець, я хочу оновлювати залишок товару, щоб не продавати те, чого вже немає.
- Як покупець, я хочу безпечно повторити запит checkout після timeout, щоб не отримати два замовлення.
- Як адміністратор, я хочу бачити проблемні платежі, щоб вручну перевіряти конфліктні випадки.

## 2. Домен

Основні сутності:

| Сутність      | Зв'язки                                                 | Навіщо потрібна                              |
| ------------- | ------------------------------------------------------- | -------------------------------------------- |
| User          | має багато Orders; може бути Seller або Customer        | Ідентифікація ролей і доступів               |
| Product       | належить Seller; має InventoryItem; входить в OrderItem | Каталог товарів                              |
| InventoryItem | належить Product                                        | Обмежений ресурс, за який конкурують покупці |
| Order         | належить Customer; має багато OrderItems; має Payment   | Незворотна бізнес-операція checkout          |
| Payment       | належить Order                                          | Фіксує оплату та її статус                   |
| Notification  | пов'язана з User та Order                               | Події для email/realtime/черги               |

Перевірка домену:

| Вимога                                      | Як закривається                              |
| ------------------------------------------- | -------------------------------------------- |
| >= 2 ролі користувачів із різними правами   | Customer, Seller, Admin                      |
| Обмежений ресурс, за який конкурують        | `InventoryItem.quantity_available`           |
| Операція з незворотним ефектом              | Створення `Order` і резервування залишку     |
| Подія, про яку треба когось сповістити      | `OrderCreated`, `PaymentFailed`, `OrderPaid` |
| Сутність із файлами                         | Фото товару для `Product`                    |
| Дані, які часто читають і рідко змінюють    | Каталог товарів і картки товарів             |
| 4-6 сутностей зі зв'язками й важким запитом | 6 сутностей описані вище                     |

## 3. Архітектурні рішення

Compute model: спочатку монолітний HTTP API на Node.js. Для курсового це простіше підтримувати, а межі домену все одно будуть виділені через модулі `products`, `orders`, `payments`, `notifications`.

База даних: PostgreSQL. Вона потрібна через транзакції під час checkout: створення замовлення, створення order items і декремент залишку мають виконуватись атомарно, інакше можливий овербукінг товару.

Асинхронність: події про створення замовлення та статус платежу будуть писатися в outbox. Це дозволить не втрачати сповіщення, навіть якщо email/realtime worker тимчасово недоступний.

Auth: JWT access token з ролями `customer`, `seller`, `admin`. RBAC буде застосовуватись на рівні маршрутів і ресурсів: продавець може змінювати тільки свої товари, покупець - тільки свої замовлення.

Deploy: Docker container для API, PostgreSQL як окремий сервіс, Redis пізніше для cache-aside каталогу. На старті локальний `docker compose` достатній, production-оточення можна додати після стабілізації API.

## 4. Trade-offs

Не роблю мікросервіси на старті. Для курсового важливіше довести коректність контракту, транзакцій і тестів, ніж платити складністю мережевих викликів між сервісами.

Не роблю реальну інтеграцію з платіжним провайдером у першій версії. `Payment` буде доменною сутністю зі статусами, а зовнішній provider можна додати пізніше через adapter, коли з'явиться outbox і retry-логіка.

Не використовую eventual consistency для декременту залишку. Для маркетплейсу це ризик овербукінгу, тому checkout має використовувати транзакцію та блокування рядків inventory.

Не додаю повнотекстовий пошук окремим сервісом на старті. Каталог спочатку працюватиме через PostgreSQL-фільтри та індекси; Elasticsearch/OpenSearch має сенс тільки після появи реальних вимог до пошуку.

Не описую двадцять API-операцій наперед. Для ДЗ#9 достатньо чесного мінімального контракту навколо `products` і `orders`, бо саме ці ресурси потім стануть основою БД, транзакцій і contract-тестів.
